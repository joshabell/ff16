1Summary & recommendation

What we need: a public leaderboard that applies the Notice of Race high-point scoring, plus tools for managing racers, race days and individual race results that only the Race Committee (RC) can use. User administration should be simple, hosting should be free, and the code should live in GitHub with automated testing and deployment (GitHub Actions).

FF16 is small. Last season had about 6 racers and 3–5 races per race day, and this season targets 12 race days. Any free tier below handles that load hundreds of times over, so the real differences are how easy it is for the RC to enter results on a cold beach, how easy it is to add or remove RC members, and how much there is to build and maintain.

Proposal A

GitHub only

Results live as data files in the repo. The RC enters them through a GitHub form. An Action recomputes the standings and publishes a static leaderboard to GitHub Pages.

Simplest to run, but the RC needs GitHub accounts.

Proposal B · Recommended

Cloudflare

A small web app on Cloudflare Workers with a SQLite database (D1). Cloudflare Access guards the RC pages with an emailed one-time code.

Best RC experience, and still free.

Proposal C

AWS serverless

S3 + CloudFront site, Lambda API, DynamoDB, and Cognito logins with a "RaceCommittee" group, all deployed with AWS CDK.

Most industry-standard, but the most setup.

Recommendation: Proposal B (Cloudflare). It gives RC members a real results-entry screen on their phones, a password-free login, and one list of emails to manage. Its free tier is permanent and doesn't go to sleep in the off-season. The build stays small: one TypeScript app and one SQLite database. If the RC is comfortable with GitHub, or we want something running within a weekend, Proposal A is a good first step. The scoring code and data format are shared, so moving from A to B later loses nothing.

2What every proposal shares

Scoring rules (from the Notice of Race §9)

Race score = (boats in the race) + (boats finishing behind you)
  • In an 8-boat race, 1st scores 8 + 7 = 15 and last scores 8 + 0 = 8.
  • A boat that does not race (DNR) scores 0.
  • Each racer drops their lowest floor(20% × races held) scores. The season total is the sum of the remaining scores.

All three proposals use the same small scoring module, written once in TypeScript as a pure function that does no database or network work. That makes it easy to test, and the test suite runs on every change in GitHub Actions. The worked example from the NoR becomes the first test:

// scoring.ts — used by all three proposals
export function raceScore(boatsInRace: number, place: number): number {
  return boatsInRace + (boatsInRace - place);       // fleet size + boats beaten
}

export function seasonTotal(scores: number[], racesHeld: number): number {
  const drops = Math.floor(racesHeld * 0.2);          // 20%, rounded down
  return [...scores].sort((a, b) => a - b)            // DNRs are already 0
    .slice(drops)
    .reduce((sum, s) => sum + s, 0);
}

// scoring.test.ts — the NoR "Alex" example must equal 107
test("NoR example", () => {
  expect(seasonTotal([13, 10, 17, 8, 14, 15, 0, 17, 9, 12], 10)).toBe(107);
  expect(raceScore(8, 1)).toBe(15);
  expect(raceScore(8, 8)).toBe(8);
});

Data model

A race day (one Sunday at one venue) holds several races. Each race has one result per boat that sailed. Racers who didn't sail a race get DNR (0) automatically, so the RC never has to enter them.

3Proposal A — GitHub only

Idea: GitHub is the whole system. Racers, race days and results are plain data files (data/*.yaml) in the repo. RC members submit results by filling in a GitHub Issue Form, which works in a phone browser or the GitHub app. A GitHub Action checks the submission, saves it to the data files, recomputes the standings, and republishes a static leaderboard site on GitHub Pages.

How it works

RC enters a race

  1. On a phone, open the repo → Issues → New → "Race results". The form asks for race day (dropdown), race number, and finish order (one racer per line, with codes like DSQ allowed).
  2. Submitting opens an issue labelled race-result. That starts the ingest workflow.
  3. The workflow refuses anyone who isn't a collaborator on the repo. It then checks the names against racers.yaml, writes the race into results.yaml, runs the scoring tests, rebuilds the site and deploys it. It finishes by commenting a link on the issue and closing it.
  4. If anything is wrong, such as an unknown racer or a duplicate place, the bot comments with the problem and leaves the issue open.

Racers and race days

Two more issue forms, "Add racer" and "Update race day" (venue, BYE or cancelled), use the same pipeline. The RC can also edit the YAML files in GitHub's web editor. Each change is a commit, so we get a full history of who changed what, and any change can be undone.

User administration

Repo Settings → Collaborators → Add people, using the person's GitHub username. That person is now RC. Removing them revokes access. Nothing else is needed.

CI workflow

# .github/workflows/ingest.yml — runs when an RC member submits the form
name: Ingest race results
on:
  issues:
    types: [opened]
jobs:
  ingest:
    # only repo owner/collaborators; anyone else's issue is ignored
    if: contains(github.event.issue.labels.*.name, 'race-result') &&
        contains(fromJSON('["OWNER","MEMBER","COLLABORATOR"]'), github.event.issue.author_association)
    runs-on: ubuntu-latest
    permissions: { contents: write, issues: write, pages: write, id-token: write }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npm run ingest -- --issue ${{ github.event.issue.number }}
      - run: npm test                        # scoring tests must pass before publishing
      - run: git commit -am "Results from #${{ github.event.issue.number }}" && git push
      - run: npm run build                   # writes site to ./dist
      - uses: actions/upload-pages-artifact@v3
        with: { path: dist }
      - uses: actions/deploy-pages@v4

Gotcha: a commit pushed by a workflow (using the built-in token) does not trigger other workflows. That's why this one workflow ingests, builds and deploys. A second ci.yml handles normal code changes: it runs tests on pull requests and deploys on pushes to main.

Free-tier fit

  • GitHub Pages is free for public repos. A private repo needs a paid GitHub plan to use Pages. The FF16 data is public anyway, so a public repo is the natural fit.
  • GitHub Actions is unlimited for public repos (2,000 min/month for private). Each run takes about 1 minute, and we'd use roughly 50–100 minutes a season.

Pros

  • $0, with no servers, databases or other accounts
  • Every change is a commit: full history and easy undo
  • Least code to write and maintain; nothing to patch
  • Leaderboard is static HTML: fast, and can't go down

Cons

  • Every RC member needs a GitHub account and must learn issues
  • 1–3 minute delay before the leaderboard updates
  • Form UX is generic (text areas, not drag-to-reorder)
  • Corrections mean editing YAML or a follow-up form

Effort: small. Roughly a weekend for the scoring, forms and site, plus a few evenings of polish.

4Proposal B — Cloudflare Recommended

Idea: a small real web app. A single Cloudflare Worker serves the public leaderboard pages and a JSON API. Data lives in Cloudflare D1, a hosted SQLite database. The RC area (/admin) and every write API sit behind Cloudflare Access. When an RC member opens /admin, Cloudflare asks for their email and sends a 6-digit one-time code. There are no passwords and no login code to write. The list of allowed emails is the Race Committee.

How it works

Public views the leaderboard

The browser loads /. The Worker reads the season's results from D1, runs the shared scoring module, and returns the page in milliseconds from a data centre near Boston. No login is needed.

RC enters a race

  1. Open scores.ff16…/admin on a phone. The first time, Access asks for an email and sends a code, and the session then lasts for days (configurable).
  2. Pick today's race day → New race. Tap racers in finishing order, mark any DNF/DSQ, then Save.
  3. The leaderboard updates immediately. Edit or Delete on any race fixes mistakes, and every change is written to an audit table (who and when).

Racers and race days

The Racers screen handles add, rename and mark inactive. The Schedule screen comes pre-filled from the NoR dates, and the RC sets venue A/B/C, marks BYE or cancelled, or uses a backup date.

User administration

  1. Cloudflare dashboard → Zero Trust → Access → Access groups → "Race Committee".
  2. Add or remove an email address and save. That's all.

Optionally, we can show the list read-only inside /admin so the RC can see who has access.

CI workflow

# .github/workflows/ci.yml
name: CI / Deploy
on:
  pull_request:                 # test every proposed change
  push:
    branches: [main]            # deploy whatever lands on main
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - run: npm test           # includes the NoR "Alex = 107" example
  deploy:
    needs: test                 # never deploy if tests fail
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - uses: cloudflare/wrangler-action@v3
        with:
          apiToken:  ${{ secrets.CLOUDFLARE_API_TOKEN }}   # stored in repo Settings → Secrets
          accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
          command: d1 migrations apply ff16 --remote
      - uses: cloudflare/wrangler-action@v3
        with:
          apiToken:  ${{ secrets.CLOUDFLARE_API_TOKEN }}
          accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
          command: deploy

5Proposal C — AWS serverless

Idea: the textbook AWS serverless stack. The site (public leaderboard + RC screens) is static files in S3 served through CloudFront. The browser calls an API on AWS Lambda, which stores data in DynamoDB. RC members log in through Amazon Cognito, and only users in the Cognito group RaceCommittee can call write endpoints. All infrastructure is defined in code with AWS CDK (TypeScript). GitHub Actions deploys it through a short-lived role (OIDC), so no AWS keys are stored in GitHub.

How it works

Public views the leaderboard

CloudFront serves the static page. The page calls GET /api/leaderboard, and the Lambda reads the season from DynamoDB, scores it and returns JSON.

RC enters a race

The RC member signs in (Cognito's hosted login page), which hands the browser a token. The same results screen as in Proposal B sends the race to POST /api/races. The Lambda checks the token's cognito:groups contains RaceCommittee, then saves.

User administration

  1. AWS console → Cognito → User pools → ff16 → Users → Create user, with their email. Cognito emails a temporary password.
  2. Open the user → Add to group → RaceCommittee.
  3. Self sign-up is disabled, so only people you create can log in.

To avoid using the AWS console at all, we could build a small "Manage RC" page that calls Cognito's admin APIs. That's more code and needs its own permission checks.

CI workflow

# .github/workflows/ci.yml (deploy job)
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      id-token: write           # lets GitHub prove its identity to AWS — no stored keys
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::<account-id>:role/ff16-github-deploy
          aws-region: us-east-1
      - run: npx cdk deploy --require-approval never

One-time setup: bootstrap CDK in the account, and create the IAM role that trusts GitHub's OIDC provider for this repo only.

Free-tier fit

  • Lambda (1M requests/month), DynamoDB (25 GB) and Cognito (Lite tier, 10,000 monthly users) have permanent free allowances far above FF16 usage. CloudFront also has a large always-free allowance.
  • S3 storage is free only during the introductory period. After that, a few MB of site files costs a few cents a month.
  • AWS changed its free-tier model for new accounts in 2025 (credit-based introductory plan). Check the current terms when creating the account, and set a $1 budget alarm on day one.

Pros

  • Industry-standard stack; good learning value
  • Fine-grained control over everything; scales without limit
  • Infrastructure as code: the whole system is rebuildable from the repo
  • Keyless deploys via OIDC

Cons

  • Most moving parts: IAM, CDK, Cognito, CloudFront
  • User admin happens in the AWS console (or needs extra code)
  • Passwords to reset; Cognito's hosted login is functional but plain
  • Not guaranteed $0: small charges are possible, and a billing account is required
  • Harder to hand over to a non-technical future Fleet Captain

Effort: large. Roughly 4–5 weekends, mostly AWS setup, CDK and auth wiring rather than the scoring itself.

7GitHub Actions primer

GitHub Actions is GitHub's built-in automation. You put a YAML file in .github/workflows/. It says when to run (the trigger) and what to run (jobs made of steps). GitHub then runs it on a fresh virtual machine. For a public repo this is free.

TermMeaning here
WorkflowOne YAML file, e.g. ci.yml. You can have several.
Trigger (on:)pull_request = test proposed changes. push to main = deploy. issues = Proposal A's form. schedule = weekly backup. workflow_dispatch = a manual "Run" button.
Job / stepA job runs on one machine, and its steps run in order. needs: test makes deploy wait for tests.
Action (uses:)A reusable step someone published, e.g. actions/checkout or cloudflare/wrangler-action.
SecretAn encrypted value in Settings → Secrets and variables → Actions (e.g. the Cloudflare API token). It's never shown in logs.
Branch protectionA rule on main requiring the test check to pass before merging, so a broken scoring change can't reach the live leaderboard.

You watch runs under the repo's Actions tab. Each run shows a live log, a green tick or a red cross, and GitHub emails you when one fails.

8Decisions & next steps

Decided (Nov 2, 2026): Proposal B (Cloudflare), public repo, launch on the free workers.dev address with an FF16 subdomain possible later. Initial Race Committee: Josh Abell. Scoring: DNF/DSQ/OCS/RET score 0 and don't count toward the race size; race size = finishers in that race; drops are based on races held; no tie-break; starting fresh with the 2026–27 season. The build lives in this folder. See README.md.

Scoring questions for the committee

The NoR defines finishes and DNR. Before building, we should agree on these, ideally in a short NoR amendment:

  1. DNF / DSQ / OCS: does a boat that starts but doesn't finish (or is disqualified) score 0 like DNR? Does it still count toward "total number of racers" for everyone else?
  2. "Total number of racers": boats on the start line for that race (assumed here), or everyone who came out that day?
  3. Drops when races are abandoned: drops are based on races actually held (assumed here), not the 12 scheduled.
  4. Ties in the season total: most firsts, then most seconds, or the last race?
  5. Last season's results: import them for history? (They used a different scoring scheme.)

Decisions for you

  • Pick a proposal (recommended: B, or A as a quick start).
  • Repo visibility: public (simplest, free Pages/Actions) or private.
  • Web address: free *.workers.dev / *.github.io, or a subdomain of the FF16 WordPress domain. The leaderboard can also be embedded in WordPress.
  • Who the initial RC members are (emails, or GitHub usernames for A).

Suggested build order

  1. Scoring module + tests (shared by all options) and GitHub Actions running them on every PR.
  2. Data model + seed the 2026–27 schedule from the NoR.
  3. Public leaderboard.
  4. RC tools: results entry first, then racers and race days.
  5. Auth / user admin, deploy pipeline, branch protection.
  6. Dry run with the RC on a real race day, then go live.
